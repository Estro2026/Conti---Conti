# Wireframe Plan

## 1. Quando usare questo documento

Usare il wireframe per:

- siti multipagina;
- progetti con architettura complessa;
- redesign con revisione importante della struttura;
- progetti che richiedono approvazione cliente prima della UI finale.

Non usarlo come passaggio obbligatorio per landing page o one-page semplici, salvo necessità specifiche.

## 2. Input necessari

Prima di iniziare il wireframe verificare che siano disponibili o analizzati:

- project-brief.md
- visual-direction.md
- ux-strategy.md
- content-strategy.md
- seo.md
- technical.md
- information-architecture.md
- current-site-audit.md, se presente sito attuale
- competitor-benchmark.md
- references.md
- sitemap cliente, se presente

## 3. Obiettivo del wireframe

Il wireframe deve definire:

- struttura;
- ordine dei contenuti;
- gerarchia;
- user flow;
- CTA;
- componenti;
- contenuti dinamici;
- form;
- relazioni tra sezioni;
- comportamento responsive principale;
- note di sviluppo;
- complessità tecnica;
- dipendenze.

Non deve ancora essere usato per decidere tutti i dettagli estetici finali.

## 6. Annotazioni obbligatorie

Ogni wireframe deve includere note quando pertinenti su:

- comportamento del componente;
- contenuto dinamico;
- CMS;
- hover;
- click;
- touch;
- sticky;
- accordion;
- carousel;
- modal;
- form;
- filtro;
- search;
- animation;
- video;
- responsive;
- elementi che cambiano ordine;
- elementi che devono mantenere struttura;
- dipendenze tecniche.

## 7. Note di sviluppo

Il Development Annotation & Estimation Agent deve aggiungere note direttamente collegate alle sezioni del wireframe.

Formato consigliato:

`DEV — comportamento / dipendenza / integrazione / responsive / stima`

Esempio:

`DEV — Carousel CMS, swipe mobile, frecce desktop, 3 card visibili desktop, 1 mobile. Stima 3–4 h.`

## 8. Stima sviluppo

Prima della consegna del wireframe deve essere disponibile:

- stima per pagina;
- stima componenti globali;
- responsive effort;
- JS / interazioni;
- CMS / integrazioni;
- QA;
- accessibilità;
- range totale ore.

La stima deve essere riportata in `development-notes.md`.

## 9. Responsive

Il Responsive & Device QA Agent deve controllare già nel wireframe:

- desktop;
- laptop;
- schermi zoomati;
- tablet;
- mobile;
- touch;
- ordine dei contenuti;
- larghezze form;
- card;
- navigazione;
- immagini;
- sticky;
- carousel;
- modal.

Le regole definitive vanno riportate in `responsive-spec.md`.

## 10. Contenuti

Il Content Agent deve verificare:

- gerarchia;
- lunghezza;
- titoli;
- CTA;
- ripetizioni;
- italiano;
- tono;
- microcopy;
- contenuti mancanti;
- contenuti da chiedere al cliente.

## 11. SEO

Il SEO Agent deve verificare:

- H1;
- H2;
- struttura contenuti;
- pagine necessarie;
- internal linking;
- search intent;
- contenuti mancanti;
- eventuali conflitti tra struttura UX e SEO.

## 12. Accessibilità

Il wireframe deve già considerare:

- ordine logico;
- heading;
- focus;
- tastiera;
- touch;
- form;
- errori;
- label;
- link;
- contenuti dinamici;
- motion reduction.

## 13. Immagini

Nel wireframe indicare:

- presenza immagine;
- funzione;
- orientamento;
- aspect ratio;
- crop;
- eventuale focal point;
- desktop / mobile;
- immagine decorativa o informativa.

Non inserire immagini casuali solo per riempire spazio.

## 14. Stati dei componenti

Quando necessario progettare:

- default;
- hover;
- focus;
- active;
- disabled;
- loading;
- empty;
- error;
- success;
- expanded;
- collapsed.
